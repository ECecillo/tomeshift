1. The symptom

The literary mode produces translations whose dominant weakness comes from the draft, not the correction. The draft is served by a self-hosted LibreTranslate/Argos instance; the LLM pass that picks it up is, by contrast, mature — series bible, locked glossary, self-healing batches, partial degradation.

The initial request was simple: replace Argos with Google Translate, then let the LLM correct against the generated dictionary. Instrumenting the pipeline to quantify this change surfaced five defects independent of Google — two of which a mere provider swap would have silently made worse.

What this document contributes

It first recalls the existing logic — because three of the five defects can only be understood by knowing precisely what the pipeline already does — then lays out the reasoning that leads to each root cause, with the measurement that establishes it placed at the moment the conclusion is drawn. The eleven chosen decisions arrive in §5.

2. What exists today

2.1 The literary pipeline end to end

Two points of this diagram will be decisive later: the TM hit branch skips the LLM correction entirely, and the budget projection is a strict pre-flight — it refuses the run before any paid call.

2.2 How HTML is neutralised: the placeholders

A natural question is whether HTML is sent to the translator. The answer is no, no structure leaves — the mechanism already does exactly what one would expect: extract the text, record the position of the elements, reinject the translation in the same place.

Three treatments depending on the node's child: a text node passes through as-is; a simple inline — whose children are all text — becomes a pair of opening/closing tokens, which keeps its inner text translatable; everything else becomes a single opaque token whose subtree is set aside. No <p>, no attribute, no structure leaves the Go process.

Why does the marker look like a tag rather than an inert [[1]]? Because it must survive the engine. With format=html, Google and LibreTranslate commit to preserving tags; a plain-text marker would be translated, moved or spaced out. The code even bears the trace of an engine that has already rewritten the token: 

// Matches both the self-closing token we emit (<x id="1"/>) and the paired
// form some providers normalize it to (<x id="1"></x>), capturing the id.
var placeholderTokenPattern = regexp.MustCompile(`<x id="(\d+)"\s*/?>(?:\s*</x>)?`)

placeholder.go:23-25 — and the choice of format=html on the adapter side: libretranslate.go:14-17.

2.3 What the LLM actually receives on each call

That's all. The LLM sees neither the whole chapter nor the other chapters. The CONTEXTE_PRECEDENT of batch i is the French translation the model has just produced itself at batch i-1 (translator.go:123-129) — this chaining forces a chapter's batches to be sequential, and it is what carries local register continuity. The chapters, by contrast, are independent: adjacentChapterText reads only the neighbours' source.

3. The reasoning: five root causes

3.1 A TM hit permanently short-circuits the correction

The segments table has source_hash as its primary key, and Lookup does not filter by engine. Let's query the actual content: 

$ sqlite3 tm.sqlite "SELECT engine, COUNT(*) FROM segments GROUP BY engine;"
literary|58
nmt-http|9

$ sqlite3 data/lumen-lit-tm.sqlite    "SELECT engine, COUNT(*) FROM segments GROUP BY engine;"
literary|83
$ sqlite3 data/lumen-review-tm.sqlite "SELECT engine, COUNT(*) FROM segments GROUP BY engine;"
literary|148

Nine nmt-http entries are anecdotal; it is the rule that matters. The raw NMT draft is persisted (orchestrator.go:772-784), and in literary mode a hit triggers a continue before the segment enters fresh (orchestrator.go:400-419):

Root cause 1

The TM mixes two kinds of data — intermediate drafts and final translations — under a key that does not distinguish them, while literary mode treats every hit as final.

3.2 The budget guardrail is calibrated to zero

The projection is a strict pre-flight, and it is well done: worst case with no TM reuse, before any provider call, plus sliding day/month caps that fail closed — a ledger read error aborts the run rather than letting it through (orchestrator.go:313-350).

But there are two cost models, and the run does not use the right one:

Model.Project / ActualModel.EstimateScenarios
Used bythe run guardrailthe estimate command only
Shapeflat: $/segment, $/1000 charsper token: input, output, overhead
Sourcemodel.goestimate.go

And the constants are zero:

$ grep -n "CostLLMPerSegment\|CostPer1000Chars" cmd/tomeshift/config.go
33:	CostPer1000CharsUSD  float64 `envconfig:"COST_PER_1000_CHARS_USD" default:"0"`
35:	CostLLMPerSegmentUSD float64 `envconfig:"COST_LLM_PER_SEGMENT_USD" default:"0"`

In literary mode, line orchestrator.go:232 therefore computes projection += 4269 × 0 = 0 $. Added to the local NMT at 0 $, the projection is zero on both sides — which is why no run has ever been blocked. The 2 $ cap exists, it has simply never had anything to compare against.

Three further discrepancies in the token model:

  • LLM_PROMPT_OVERHEAD_TOKENS defaults to 200; the actual measured prefix is ~3,000 tokens.
  • It is multiplied by the number of segments and not of calls: in = tokensFromChars(chars) + segs*rates.PromptOverheadTokens (estimate.go:67). With batches of 50, this over-counts by a factor of ~33.
  • The prompt cache is not modelled, even though it removes ~90% of the prefix on the Anthropic side.
Root cause 2

These discrepancies partly offset each other, which is the worst case: the figure looks plausible and is wrong. And the projection is only pre-flight — nothing stops a run whose actual spend drifts.

3.3 Restore mutates the tree before validating

The caller's comment announces a fallback:

"A restore failure leaves the original (source) markup in place; QA will flag the dropped placeholder. Do not abort the whole run."
— orchestrator.go:702-707

That is not what the code does:

Root cause 3

QA counts the discrepancy (placeholder_restore_ratio) and fails the run, so nothing escapes silently globally. But the documented fallback does not exist: content is lost instead of being preserved.

3.4 The stable prefix dominates the input cost

Let's first measure the actual volume, with the pipeline's own segmentation:

$ go run ./cmd/tomeshift estimate --input "books/lumen/en/Lumen LN - Volume 01.epub"

Then the actual size of the prefix, in the bible v3 actually used:

            'adresse='||length(address_json) FROM bibles;"

Conclusion already drawn upstream

This analysis was already done and already fixed on main. Commit a9dd615 raises defaultBatchSize from 10 to 50 with this comment:

"It is deliberately large. Every call repeats the stable prefix (bible plus glossary), so splitting a chapter that the model could have answered in one pass multiplies input tokens for nothing […] Prompt caching absorbs that on Anthropic but not on OpenAI-compatible hosts."

This RFC therefore does not revisit the batch size. It does, however, draw the consequences for the cost model: at batch 50 the prefix still weighs 49% of the input, and a projection that ignores the cache is pessimistic by a factor of ~1.6 — enough to refuse a run that would cost 1.41 $ under a 2 $ cap.

Root cause 4

A run's cost is not proportional to the translated text but to the number of calls, and neither of the repository's two cost models can express this dependency or the cache effect.

3.5 The draft is the weak link, and it is cheap to replace

This is the original root cause, and the only one that motivated the request. It is confirmed but it is also the least costly to address: at the user's volume, the Google draft is free.

4. Provider choice and cost matrix

4.1 The free tier, and its trap

Cloud Translation offers 500,000 characters per month, permanent — not a 12-month promotion. Two details verified against the official documentation, the second having corrected an initial misreading:

  • The quota is shared between Basic (v2) and Advanced (v3): "the first 500,000 characters sent to the API to process (Basic and Advanced combined) per month are free". There is no 1M total.
  • It is per project, and requires a GCP project with billing enabled.

A volume is ~450,000 characters. Hence, per volume:

Draft engine1 vol/month2 vol/month4 vol/month
Self-hosted LibreTranslate (current)0 $0 $0 $
Google Cloud Translation v20 $4.00 $6.50 $
DeepL Developer1M chars total ⇒ two volumes, once
DeepL Growth (26 $/month)26.00 $13.00 $6.50 $

DeepL is rejected on availability, not on quality. As of July 2026, API Free and API Pro are no longer sold to new customers; the Developer plan grants 1M characters total and Growth costs 26 $/month fixed. Google only reaches parity with Growth at four volumes per month.

Two arguments settle it in favor of v2. Authentication: NMTAPIKey already exists in the config, so an environment variable suffices, whereas v3 imposes a service account and credentials to plumb through Docker and CI — for zero translation-quality gain. And the native glossary would not replace Protect/Apply: the latter protects the locked terms both on the NMT side and on the LLM side (translator.go:218). A Google glossary would cover only the NMT step, and the project would maintain two sources of truth for twelve terms.

The v3-exclusive models were costed then rejected: Translation LLM (10 $/M input + 10 $/M output) costs ~9.70 $/volume and Adaptive Translation (25 $ + 25 $) ~24 $/volume, against 1.41 $ for Google NMT + Haiku 4.5 — and neither accepts the bible or the address rules.

That is not where the risk lies — the risk is a whole volume badly translated to proofread by hand. Cost should therefore not decide; measured quality should. Hence decision 11.

5.1 Decision 12 — what the Sonnet 5 migration actually contains

The adapter was audited change by change. Most breaking changes do not apply, only one does, and the expensive part is not a breaking change.

What does not concern you

anthropicRequest carries neither temperature, top_p nor top_k (anthropic.go:37-43): the removal of sampling parameters is a non-event. Messages are system + user only, so the assistant-prefill rejection does not apply. output_config.format already uses the current shape and not the deprecated output_format. Manual thinking (budget_tokens) was never used.

The one breaking change that affects you

Whether adaptive thinking improves literary post-editing is a legitimate question — but it is a fifth arm of the comparison, not a default to inherit by omission.

Refusals and truncations are currently invisible

anthropicResponse decodes content and usage, but not stop_reason (anthropic.go:54-65). Sonnet 5 ships elevated cybersecurity safeguards and can return stop_reason: "refusal" on an HTTP 200 with empty or partial content. Combined with the truncation risk above, two distinct failures would both surface in the same form: "decodeResponse failed, retry on halved batches". Surfacing stop_reason makes them diagnosable for a few lines.

The expensive part is the tokenizer, not the price

Sonnet 5 uses the Opus 4.7-family tokenizer: roughly 30% more tokens for the same text than Sonnet 4.6. The sticker price is identical (3 $/15 $), so the effective cost rises by the same amount.

ModelSticker priceTokensCurrent context+ chapter
claude-sonnet-4-6 (today)3 $/15 $1.00×4.22 $4.93 $
claude-sonnet-5, intro rate2 $/10 $1.30×3.66 $4.27 $
claude-sonnet-5, standard rate3 $/15 $1.30×5.49 $6.40 $
The fact that matters

The introductory rate runs until 31 August 2026 — thirty days from this RFC. Until then the migration is cheaper than the status quo; afterwards it is ~52% dearer per volume (6.40 $ against 4.22 $, chapter context included): 30% comes from the tokenizer, the rest from the enlarged cacheable prefix. It is a quality trade-off, not a saving — and the per-book cap must be calibrated on the post-August figure, otherwise it will start refusing runs a month later for no visible reason.

Consequence for decisions 6 and 9: the character→token heuristic becomes model-dependent. A LLM_TOKEN_MULTIPLIER (default 1.0) is added alongside the rates and applied on top of charsPerToken, mirroring Rates.token_multiplier in scripts/cost_model.py. Without it, the guardrail under-projects Sonnet 5 by 30%, and the measured prefix of decision 9 would inherit the same error.

What the comparison must verify, and cannot assume

Sonnet 5 follows instructions more literally than Sonnet 4.6. The system prompt opens with RÈGLES ABSOLUES in capitals, and ba84ade already had to soften a rule that was pushing the model to translate proper nouns against the glossary. More literal compliance could revive that class of conflict — glossary_violations in the run report is the detector. Response length also calibrates to perceived complexity rather than to a fixed verbosity, which should be inert for a fixed-schema JSON reply, but remains to be confirmed.

Decision 4 — scope clarification

resolveTranslation is shared by both modes. In nmt mode, the draft is the final output of a non-escalated segment, so removing the save everywhere would lose all TM reuse for that mode. The rule is "do not persist the draft in literary mode", not "never persist".

Decision 5 — it absorbs another

A placeholder integrity check right at the NMT output was considered, then dropped: Restore is called per chapter (orchestrator.go:456-465), not at the end of the book. The cost of undetected damage is therefore about three LLM calls, not a volume. With an atomic Restore the fallback truly exists, which is enough.

6. Why the chapter and not the whole book

The natural worry is this: if we correct chapter by chapter without knowing whether the style of chapter 1 is consistent with that of chapter 2, do we not create inconsistencies? The answer requires separating two problems that are easily conflated.

Style coherence is not inferred, it is specified — by a frozen document, byte-identical in all 130 calls. Excerpt from the GUIDE_DE_STYLE actually stored in bible v3:

"Epithets ('Old Man Bram', 'Pops', 'scar-faced man') are consistent across chapters. Register fidelity: do not add oral fillers, interjections or discourse markers (e.g. « ouais », « bon », « bah », « hein ») that are absent from the source. […] Lexical consistency: keep the same word for recurring concrete nouns across the volume (e.g. always « survêtement », never « survêt' »)."

This is stronger than a model's memory: deterministic, auditable via just bible, non-degrading over 68 chapters, and carried from one volume to the next.

The decisive argument against whole-book context

The "whole-book" context would supply the LLM with the English of previous chapters. Yet the worry is about the French produced — "did I translate this word the same way in chapter 1?". That information is nowhere in the whole-book context. To truly provide it one would have to inject the accumulated FR translation: ~148k tokens by the end of a volume, changing with every chapter so uncacheable, for 9 to 15 $/volume and maximum dilution risk. The glossary and the lexical-consistency rule do that job for 0 $.

6.1 The real problem with --update-bible, quantified

Correction of an earlier formulation

An earlier reading presented as a defect the fact that "the specification is no longer the same from one end of the volume to the other". It is not one. A human translator working on chapter 2 does not know chapter 50 either: the asymmetry reproduces the reading order and is defensible. The real defects are elsewhere, and they are measurable.

updateBible mutates the bible in place at the end of each chapter, and the same pointer serves the next chapter (orchestrator.go:467-475, then 483-513). Since stablePrefix embeds RESUME_DE_L_HISTOIRE, the cacheable prefix changes with every chapter. The summaries actually stored measure 301, 1,511 and 1,067 characters, i.e. 274 tokens on average: 

prefix: 2,997 tokens at chapter 1  →  21,355 tokens at chapter 68
Frozen bibleEvolving bible
Prefix cost (Sonnet 4.6)0.13 $3.33 $
Cache writes168
Re-run of the same book0 $3.33 $ + the whole LLM pass

Three defects, then:

  1. +3.20 $ per volume — more than the entire Google draft, and of the same order as the whole LLM pass (4.22 $). The prefix ends up 7× bigger than at the start and is rewritten in cache 68 times instead of once.
  2. Re-runs stop being free and reproducible. llm_cache.sqlite is keyed by model + messages. With a frozen bible, a re-run costs 0 $. With --update-bible, the bible on disk has changed since the previous run, so the chapter 1 prompt differs, so zero hits: the whole pass is paid again. And the operation is not idempotent — on the first run chapter 1 sees 0 summaries, on the second it sees 68.
  3. Version does not move. updated.Version = bible.Version: the content evolves, the number stays. just bible displays v3 whether the bible contains 3 summaries or 70 — which explains the current state, the versions coming from style-profile and not from --update-bible.

6.2 The fix: a pre-generated bible — RFC 0008

The right answer is to build the bible before any translation, from all available volumes, and to regenerate it only when a new volume is released. A translation run then consumes a frozen artefact and never writes to it. This fixes the three defects at once. But instrumenting it revealed a blocker and a cost trap.

The blocker: chapter identifiers collide across volumes

Corroborating clue: the real bible's summaries are keyed prologue, 1, 2 — not in the ch_0001 format. They therefore come from seeding by style-profile, not from --update-bible during a run. This incremental path has probably never run, which explains the version stuck at 3.

The cost trap: "as complete as possible" is paid pro rata

Bible variantPrefix tokens$/volume
--update-bible (current behaviour)2,997 → 21,3554.33 $
Frozen, 3 summaries (state of affairs today)2,9970.17 $

Sonnet 5, standard rate, 130 calls. Keeping per-chapter summaries in pre-generation would cost more from 5 volumes on than the behaviour we are trying to remove.

Hence the choice of one synopsis per volume, which is not just a saving: the summary of chapter 42 of volume 7 is noise when translating chapter 3 of volume 1. What the translator needs to know about the other volumes is the arc — and decision 10 already provides the full source of the current chapter for local detail.

The scope: bounded to volumes 1..N

bible used to translate volume N   (frozen for the whole run)
  GUIDE_DE_STYLE        ← all available volumes
  VOIX_DES_PERSONNAGES  ← all available volumes
  REGLES_TU_VOUS        ← all available volumes
  RESUME_DE_L_HISTOIRE  ← volumes 1..N only

The style, the voices and the address rules are drawn from the whole series: that is where completeness is wanted and it is almost free. Only the narrative summaries are bounded — so as not to give the ending to the model. This is not an abstract precaution here: your style guide states that the horror of Return by Ash rests on a factual description in the loop sections, an effect that depends on not knowing. A model knowing the true nature of a character revealed in volume 8 can colour its volume 1 dialogue.

How a volume's synopsis is produced

No existing operation fits. Profiler.Seed(samples []string) makes one call and returns a whole bible from samples, Update does the same after a chapter — and both do a full bible round-trip, which a synopsis does not need.

The distinction that decides

Sampling is the right method for style and the wrong one for plot. Register, tone and idiolects are inferred from five excerpts — that is exactly the raison d'être of Seed. A synopsis, no: one does not summarise a story from selected snippets. Two distinct extraction problems, two distinct methods.

ModelA — 1 call / volumeB — map-reduce
Haiku 4.50.12 $0.18 $
Sonnet 4.60.36 $0.55 $
Sonnet 5, standard rate0.47 $0.71 $

A one-off cost per volume, never replayed: over 15 volumes on Sonnet 4.6, 5.46 $ against 8.24 $ for the life of the project. Cost therefore does not decide. What decides is that option A compresses 298:1 in a single pass — the model must hold a whole novel and judge alone what matters. Lost-in-the-middle degradation is a documented failure mode, and a silent one: the synopsis would read well on the opening and the ending, hollow in the middle, with nothing to signal it to you. Map-reduce reads each chapter at 4:1 then reduces at 47:1 — two comfortable ratios.

The rest of the detail — schema change, mergeSummaries made explicit rather than silently destructive, migration of the single curated bible — is in RFC 0008. The two RFCs compose without conflict: 0007 puts the chapter source in the prefix, 0008 guarantees that the rest of the prefix does not move.

7. Sequencing in four batches

The ordering is load-bearing. Decision 10 changes the prompt: it invalidates the LLM cache and alters quality. Shipped alongside Google, it would make the decision-11 comparison unable to distinguish the draft effect from the context effect.

Batch 1 prerequisite: rebase google-translate-api onto a9dd615. The branch is one commit behind, and that commit changes precisely defaultBatchSize.

The measurement tooling already exists: books/lumen/ch1/fr-ch1.epub is a human translation of chapter 1 and eval --reference computes chrF against it (eval.go:26). Mind the interpretation: chrF measures agreement with that precise translation, not absolute quality — hence the cross-check with COMET-QE and a three-column read.

8. What we do not do

  • Parallelising chapters during the LLM pass. Feasible — chapters are independent — and it is the largest remaining latency lever, but it is a separate effort. Order of magnitude for WN vol. 1: the draft drops from ~14 min to ~30 s thanks to batching, while the LLM pass remains the bottleneck.
  • The pre-generated bible — handled, but in RFC 0008 and not here: dedicated command, schema change, new summary path. See §6.2.
  • v3's Translation LLM and Adaptive Translation (§4.2).
  • Fuzzy TM, PostgreSQL migration (RFC 0005), and any change to the QA gate.

Limits of the method

The character→token conversions are named heuristics centralised in scripts/cost_model.py (4.0 chars/token in English, 3.5 in French, 1.15 expansion). They reuse charsPerToken from estimate.go:11.
