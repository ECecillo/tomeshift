1. L'avis en une minute

Oui, Temporal se prête bien à ce projet — pour la forme du problème, pas pour son échelle. Un run est long (des heures), multi-étapes, dépendant de fournisseurs externes à quota, et il ne doit jamais payer deux fois. C'est la définition d'un workflow durable. L'échelle, elle, est minuscule : un utilisateur, un livre à la fois. Temporal est donc surdimensionné en capacité, mais pas en fonctions : chacune de celles qu'il apporte correspond à un mécanisme aujourd'hui écrit à la main, ou planifié dans M4.

Le prix, énoncé
  • Un service toujours allumé pour run — un conteneur SQLite, zéro coût externe. estimate reste hors-ligne.
  • Une dépendance lourde (go.temporal.io/sdk → gRPC, protobuf), à inscrire dans DEPENDENCIES.md.
  • Le code de workflow doit être déterministe : pas d'I/O, pas de time.Now, pas de goroutine, pas d'itération de map qui décide.
  • Le vrai chantier : les segments tiennent aujourd'hui un pointeur vers l'arbre HTML vivant (segment.Segment.Node), que Restore mute et que Recompose rend. Rien de cela ne peut traverser une frontière d'activité (limite 2 Mo par payload). Il faut découpler — et c'est un refactor qui a de la valeur même sans Temporal.
La recommandation

Adopter Temporal sous cinq conditions : les activités sont les fonctions d'étape existantes ; un seul moteur à la fin (le chemin in-process est supprimé) ; ce sont des références qui traversent Temporal, pas du contenu ; serveur de dev local en SQLite, pas de Postgres ; un worker, un slot d'activité, tant que la TM est en SQLite.

2. La topologie cible

Ce qui change pour l'opérateur : just up démarre temporal et le worker ; just run démarre un workflow et suit sa progression ; l'UI est sur localhost:8233. Les recettes qui appellent un fournisseur enveloppent désormais le worker dans op run, plus le CLI — ce qui règle au passage le problème de la barre éteinte par le tube de 1Password.

3. Le cycle de vie d'un run

Un livre = un workflow TranslateBook. Chaque étape de l'orchestrateur actuel devient une activité avec son timeout et sa politique de retry ; le workflow ne fait que les enchaîner et additionner ce qu'elles ont consommé. Lancez l'animation, puis tuez le worker en cours de route : l'historique survit, le worker redémarre, les activités terminées sont rejouées (aucun appel), et l'exécution reprend là où elle s'était arrêtée.

Où va l'état

Aujourd'hui les compteurs vivent dans RunResult, alimentés par le delta du compteur de caractères et par le hook OnBatch (mode.go:218-226). Demain chaque activité retourne ce qu'elle a consommé (caractères, tokens, tentatives, hits TM) et le workflow additionne. L'historique Temporal devient la piste d'audit dont le ledger était la seule copie — et le prix se calcule par une activité locale PriceRun, arithmétique pure sur le modèle de coût.

4. Un chapitre littéraire, lot par lot, avec un 429

C'est la scène qui justifie le chantier. Un chapitre de 100 segments part en 2 à 4 lots LLM. Aujourd'hui, si le troisième lot reçoit un 429, llm.ErrRateLimited stoppe le chapitre et fait échouer le run (literary/translator.go:194-197) : les lots 1 et 2, réussis mais non persistés, sont perdus et seront repayés à la relance. Avec Temporal, RefineBatch est l'unité de retry : le workflow passe en paused, attend, et relance le même lot.

Aujourd'hui — run en échec, chapitre refait

lots payés au total 0
les lots réussis avant le 429 ne sont pas persistés (persist n'a lieu qu'après Restore, en fin de chapitre)

lots payés au total 0
le lot 3 est rejoué ; les lots 1-2 sont dans l'historique et dans le cache de complétions
Pourquoi le lot et pas le chapitre

La reprise se fait à la granularité de l'activité qui a échoué. Une activité RefineChapter garderait la frontière actuelle ; RefineBatch la descend au lot. La division récursive d'un lot tronqué (TranslateChapter) reste dans l'activité : ce sont les mêmes tokens, pour le même lot logique. Le tail de ~1 200 runes de français précédent voyage dans le payload — 3 Ko, rien.

5. Ce qui traverse Temporal — et ce qui ne le fait jamais

Temporal persiste chaque entrée et chaque sortie d'activité dans l'historique. La limite est de 2 Mo par payload (avertissement à 256 Ko) et de 51 200 événements par run. Le livre en octets, les arbres *html.Node, les placeholders avec leur nœud : rien de cela ne passe. C'est le motif claim-check : le contenu reste dans un espace de travail sur disque, les activités s'échangent des références et des compteurs.

Budget de payload sur vol33 (45 chapitres, 4 774 segments, 101 appels LLM)

plusieurs MoRawEPUB.Files — ne passe PAS

Un test sur le livre fixture affirmera ces tailles contre le seuil de 256 Ko, pour attraper la dérive.

Le refactor préalable, sans Temporal (phase 1)

La segmentation est déterministe : ids par position, hash du texte normalisé. Un process qui ne détient que {segment_id, target_text} peut donc re-parser le document d'origine, re-dériver les placeholders, Restore pour valider, et rendre. C'est epub.ApplyTranslations(book, units). CommitChapter l'utilise pour valider et persister par chapitre ; RecomposeBook pour produire le livre. Le critère d'acceptation est l'identité octet à octet de translated.epub avant et après, sur la fixture et sur un chapitre réel entièrement en TM.

Idempotence — une activité peut tourner deux fois
  • TM.Save : upsert sur source_hash, déjà idempotent.
  • RecordRun : une ligne par tentative voulue ; une activité réessayée n'en est pas une → colonne attempt_key = WorkflowID/RunID, index unique, INSERT OR IGNORE.
  • WriteArtifacts : écrase, idempotent.
  • DraftChapter réessayé repaie les caractères NMT — contrat actuel de RetryingTranslator.
  • RefineBatch réessayé est servi par llm_cache.sqlite si la tentative précédente avait obtenu une réponse.
Déterminisme — les règles du package workflow
  • workflow.Now, jamais time.Now ; workflow.SideEffect pour tout aléa.
  • Aucune I/O, aucun appel réseau, aucune goroutine.
  • Aucune itération de map qui influence une décision.
  • Pas de mise à jour du worker en cours de tome ; sinon workflow.GetVersion.
  • Un test de replay sur un historique enregistré du livre fixture tourne en CI.

7 bis. Découpage du code et couplage à Temporal

Exigence posée : pouvoir demain changer de moteur — ou revenir à aucun — en réécrivant un seul package. Réponse : ports et adaptateurs, avec tout le métier du côté sans Temporal, y compris le flux de contrôle. Le workflow Temporal n'est qu'une ligne : return pipeline.RunBook(steps, runtime, in).

Les deux ports — c'est tout ce que le flux connaît du moteur 
// Steps : une méthode par activité, sans contexte —
// l'adaptateur le possède (workflow.Context n'est
// pas un context.Context).
type Steps interface {
    PrepareBook(BookInput) (Manifest, error)
    ProjectCost(ProjectInput) (Projection, error)
    ResolveChapter(ResolveInput) (ChapterPlan, error)
    DraftChapter(DraftInput) (DraftResult, error)
    EscalateChapter(EscalateInput) (EscalateResult, error)
    RefineBatch(RefineInput) (RefineResult, error)
    CommitChapter(CommitInput) (CommitResult, error)
    UpdateBible(BibleInput) (BibleResult, error)
    RecomposeBook(RunRef) (RecomposeResult, error)
    CheckEPUB(CheckInput) (CheckResult, error)
    FinishBook(FinishInput) (qa.Report, error)
    RecordSpend(SpendInput) error
    PriceRun(PriceInput) (float64, error)
}

// Runtime : ce dont le flux a besoin d'un moteur,
// et rien de plus.
type Runtime interface {
    Now() time.Time
    WaitResume(d time.Duration) (resumed bool, err error)
    Paused() bool
    Cancelled() bool
    Detached() Runtime
    Report(Progress) // le flux publie ; in-process → barre, Temporal → query
    RunBook(BookInput) (RunResult, error) // série : un enfant par tome
}

La règle d'import est vérifiée, pas espérée : une règle depguard dans .golangci.yml interdit go.temporal.io/** partout sauf dans internal/temporal et internal/commandexec. golangci-lint garde déjà chaque commit.

Le compromis, énoncé

Les ports sont un vocabulaire fixe. Une fonctionnalité Temporal que le flux voudrait (un Update, un appel Nexus) passe d'abord par une méthode de port. Pour une pipeline séquentielle de 13 étapes c'est le bon prix ; l'alternative — écrire le flux en appels workflow.* — c'est ~300 lignes à réécrire à chaque changement de moteur, avec tous les tests qui les exercent. Ce que l'adaptateur n'abstrait pas : les préoccupations propres à Temporal (codecs de payload, files, options du worker, GetVersion, replay). Elles vivent dans internal/temporal et partent avec lui.

Étendre : ajouter un mode de traduction (ex. LLM seul)

Un mode est une recette sur les Steps existants, jamais un nouveau workflow. RunBook choisit un Mode d'après BookInput.Mode, que le workflow transmet sans le lire. nmt = Resolve → Draft → Escalate → Commit ; literary = Resolve → Draft → RefineBatch × n → Commit ; llm = Resolve → RefineBatch × n sans brouillon → Commit.

Un mode qui exigerait une nouvelle étape coûte, côté adaptateur, une méthode de Steps, une méthode de Stages, un enregistrement d'activité et une ligne de policy.go — ~30 lignes mécaniques. Le vrai coût du mode LLM seul n'est pas le code : le filet de sécurité des placeholders retombe aujourd'hui sur le brouillon NMT ; sans brouillon il retomberait sur la source anglaise. Soit on re-tente le segment dégradé seul, soit on demande un brouillon à la demande pour les seuls ids dégradés (DraftChapter sur un sous-ensemble — l'étape existe). À trancher quand ce mode se fera ; untranslated_segments en QA attrape le cas dans les deux options.

8 bis. Les tests, lot par lot

Cinq niveaux, du plus rapide au plus lourd. Les quatre premiers tournent sans serveur Temporal et entrent dans just check ; le cinquième démarre le dev server comme service de la CI (le conteneur boote en ~2 s) et se skip en local si :7233 est injoignable — le motif déjà en place pour ollamaHost. L'API de test du SDK n'est utilisée qu'au niveau 3, sur le seul package qui importe le SDK.

Ce que le niveau 2 permet, et qui manquait

Le flux tourne sur un Runtime in-process dont le timer est un channel : un cooldown de 30 min se « saute » en fermant le channel, un resume s'envoie depuis le test. Le scénario « 429 au milieu d'un tome → pause → reprise → même facture » — que la session 18 a laissé sans test parce qu'il exigeait un vrai serveur et de vraies minutes — devient un test Go ordinaire de quelques millisecondes, sans SDK. Et parce qu'il tourne aussi dans le workflow, le test de replay (niveau 4) garantit qu'il reste déterministe.

10. Les décisions — toutes tranchées le 10 septembre 2026

  1. Plafond dépassé → décidé échouer comme aujourd'hui (ErrBudgetExceeded avant tout appel). Pas de signal approve-budget.
  2. Cooldown du rate limit → décidé 30 min, doublant à chaque attente consécutive, plafond 5 h (fenêtre du CLI Claude).
  3. run bloquant ou --detach → décidé bloquant : une commande, la barre de progression nourrie par la query progress, un code de sortie. Le run survit quand même au CLI puisqu'il vit dans le worker. Pas de --detach dans ce RFC.
  4. Files de tâches → décidé une seule, epub-translator.
  5. Temporal Schedules → décidé après la phase 5, seulement si le besoin apparaît.
