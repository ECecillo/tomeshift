1. The one-minute verdict

Yes, Temporal fits this project well — for the shape of the problem, not for its scale. A run is long (hours), multi-stage, dependent on quota-bound external providers, and it must never pay twice. That is the definition of a durable workflow. The scale, though, is tiny: one user, one book at a time. Temporal is therefore oversized in capacity, but not in functions: every one it brings matches a mechanism written by hand today, or planned for M4.

The price, stated
  • An always-on service for run — one SQLite container, zero external cost. estimate stays offline.
  • A heavy dependency (go.temporal.io/sdk → gRPC, protobuf), to record in DEPENDENCIES.md.
  • Workflow code must be deterministic: no I/O, no time.Now, no goroutine, no map iteration that decides.
  • The real work: segments today hold a pointer into the live HTML tree (segment.Segment.Node), which Restore mutates and Recompose renders. None of that can cross an activity boundary (2 MB per-payload limit). It must be decoupled — and that is a refactor worth doing even without Temporal.
The recommendation

Adopt Temporal under five conditions: activities are the existing stage functions; one engine at the end (the in-process path is deleted); references cross Temporal, not content; a local SQLite dev server, no Postgres; one worker, one activity slot, as long as the TM is on SQLite.

2. The target topology

What changes for the operator: just up starts temporal and the worker; just run starts a workflow and follows its progress; the UI is at localhost:8233. The recipes that call a provider now wrap the worker in op run, no longer the CLI — which also fixes the bar being killed by the 1Password pipe.

3. The lifecycle of a run

One book = one TranslateBook workflow. Each stage of the current orchestrator becomes an activity with its own timeout and retry policy; the workflow only chains them and sums what they consumed. Start the animation, then kill the worker along the way: the history survives, the worker restarts, the finished activities are replayed (no call), and execution resumes where it left off.

Where the state goes

Today the counters live in RunResult, fed by the character meter delta and by the OnBatch hook (mode.go:218-226). Tomorrow each activity returns what it consumed (characters, tokens, attempts, TM hits) and the workflow sums it. The Temporal history becomes the audit trail the ledger used to be the only copy of — and the price is computed by a local PriceRun activity, pure arithmetic over the cost model.

4. A literary chapter, batch by batch, with a 429

This is the scene that justifies the work. A 100-segment chapter goes out in 2 to 4 LLM batches. Today, if the third batch gets a 429, llm.ErrRateLimited stops the chapter and fails the run (literary/translator.go:194-197): batches 1 and 2, succeeded but not persisted, are lost and will be paid again on re-launch. With Temporal, RefineBatch is the retry unit: the workflow goes paused, waits, and re-runs the same batch.

Why the batch and not the chapter

Resume happens at the granularity of the activity that failed. A RefineChapter activity would keep the current boundary; RefineBatch drops it to the batch. The recursive halving of a truncated batch (TranslateChapter) stays inside the activity: the same tokens, for the same logical batch. The ~1,200-rune tail of preceding French travels in the payload — 3 KB, nothing.

5. What crosses Temporal — and what never does

Temporal persists every activity input and output in the history. The limit is 2 MB per payload (warning at 256 KB) and 51,200 events per run. The book in bytes, the *html.Node trees, the placeholders with their node: none of that passes. This is the claim-check pattern: the content stays in a workspace on disk, the activities exchange references and counters.

A test on the fixture book will assert these sizes against the 256 KB threshold, to catch drift.

The prerequisite refactor, without Temporal (phase 1)

Segmentation is deterministic: ids by position, hash of the normalized text. So a process that holds only {segment_id, target_text} can re-parse the original document, re-derive the placeholders, Restore to validate, and render. That is epub.ApplyTranslations(book, units). CommitChapter uses it to validate and persist per chapter; RecomposeBook to produce the book. The acceptance criterion is the byte-for-byte identity of translated.epub before and after, on the fixture and on a real chapter fully in the TM.

Idempotency — an activity can run twice
  • TM.Save: upsert on source_hash, already idempotent.
  • RecordRun: one row per intended attempt; a retried activity is not one → attempt_key column = WorkflowID/RunID, unique index, INSERT OR IGNORE.
  • WriteArtifacts: overwrites, idempotent.
  • A retried DraftChapter re-pays the NMT characters — the current contract of RetryingTranslator.
  • A retried RefineBatch is served by llm_cache.sqlite if the previous attempt got an answer.
Determinism — the rules of the workflow package
  • workflow.Now, never time.Now; workflow.SideEffect for anything random.
  • No I/O, no network call, no goroutine.
  • No map iteration that influences a decision.
  • No worker upgrade mid-volume; otherwise workflow.GetVersion.
  • A replay test over a recorded history of the fixture book runs in CI.

7a. Code layout and coupling to Temporal

Stated requirement: to be able, tomorrow, to switch engine — or go back to none — by rewriting a single package. Answer: ports and adapters, with all the business on the Temporal-free side, including the control flow. The Temporal workflow is one line: return pipeline.RunBook(steps, runtime, in).

The two ports — all the flow knows about the engine 
// Steps: one method per activity, no context —
// the adapter owns it (workflow.Context is not
// a context.Context).
type Steps interface {
    PrepareBook(BookInput) (Manifest, error)
    ProjectCost(ProjectInput) (Projection, error)
    ResolveChapter(ResolveInput) (ChapterPlan, error)
    DraftChapter(DraftInput) (DraftResult, error)
    EscalateChapter(EscalateInput) (EscalateResult, error)
    RefineBatch(RefineInput) (RefineResult, error)
    CommitChapter(CommitInput) (CommitResult, error)
    UpdateBible(BibleInput) (BibleResult, error)
    RecomposeBook(RunRef) (RecomposeResult, error)
    CheckEPUB(CheckInput) (CheckResult, error)
    FinishBook(FinishInput) (qa.Report, error)
    RecordSpend(SpendInput) error
    PriceRun(PriceInput) (float64, error)
}

// Runtime: what the flow needs from an engine,
// and nothing more.
type Runtime interface {
    Now() time.Time
    WaitResume(d time.Duration) (resumed bool, err error)
    Paused() bool
    Cancelled() bool
    Detached() Runtime
    Report(Progress) // the flow publishes; in-process → bar, Temporal → query
    RunBook(BookInput) (RunResult, error) // series: one child per volume
}

The import rule is enforced, not hoped for: a depguard rule in .golangci.yml denies go.temporal.io/** everywhere except in internal/temporal and internal/commandexec. golangci-lint already gates every commit.

The tradeoff, stated

The ports are a fixed vocabulary. A Temporal feature the flow would want (an Update, a Nexus call) goes through a port method first. For a 13-step sequential pipeline that is the right price; the alternative — writing the flow in workflow.* calls — is ~300 lines to rewrite on every engine change, together with all the tests that exercise them. What the adapter does not abstract: Temporal's own concerns (payload codecs, task queues, worker options, GetVersion, replay). They live in internal/temporal and leave with it.

Extending: adding a translation mode (e.g. LLM-only)

A mode is a recipe over the existing Steps, never a new workflow. RunBook selects a Mode from BookInput.Mode, which the workflow forwards without reading it. nmt = Resolve → Draft → Escalate → Commit; literary = Resolve → Draft → RefineBatch × n → Commit; llm = Resolve → RefineBatch × n without a draft → Commit.

A mode that needs a new step costs, on the adapter side, one Steps method, one Stages method, one activity registration and one policy.go line — ~30 mechanical lines. The real cost of an LLM-only mode is not the code: the placeholder safety net falls back today on the NMT draft; without a draft it would fall back on the English source. Either retry the degraded segment alone, or request a draft on demand for the degraded ids only (DraftChapter on a subset — the step exists). To decide when that mode is built; untranslated_segments in QA catches the case in both options.

8a. The tests, batch by batch

Five levels, fastest to heaviest. The first four run without a Temporal server and fit in just check; the fifth starts the dev server as a CI service (the container boots in ~2 s) and skips locally if :7233 is unreachable — the pattern already in place for ollamaHost. The SDK test API is used only at level 3, on the one package that imports the SDK.

What level 2 allows, and what was missing

The flow runs on an in-process Runtime whose timer is a channel: a 30-min cooldown is "skipped" by closing the channel, a resume is sent from the test. The scenario "429 in the middle of a volume → pause → resume → same bill" — which session 18 left without a test because it required a real server and real minutes — becomes an ordinary Go test of a few milliseconds, without the SDK. And because it also runs inside the workflow, the replay test (level 4) guarantees it stays deterministic.

10. The decisions — all settled on September 10, 2026

  1. Cap exceeded → decided fail as today (ErrBudgetExceeded before any call). No approve-budget signal.
  2. Rate-limit cooldown → decided 30 min, doubling on each consecutive wait, ceiling 5 h (the Claude CLI window).
  3. Blocking run or --detach → decided blocking: one command, the progress bar fed by the progress query, an exit code. The run still survives the CLI since it lives in the worker. No --detach in this RFC.
  4. Task queues → decided a single one, tomeshift.
  5. Temporal Schedules → decided after phase 5, only if a need appears.
