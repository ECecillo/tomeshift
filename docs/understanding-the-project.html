1. What the program does

tomeshift is a Go CLI that translates an EPUB book from English to French without breaking the book: the file structure, the formatting, the inline tags (<em>, links, notes), and the chapter order come out intact. It is built around three obsessions, in this order:

  1. Lose nothing. Markup is extracted before translation and put back after, and the operation is atomic: if it cannot be faithful, the source is kept rather than emitting broken HTML.
  2. Don't pay twice. Translation memory, LLM completion cache, cacheable prompt prefix, the NMT provider's free tier: anything already translated or already sent is not paid for again.
  3. Never spend blindly. A run projects its worst-case cost before the first network call and stops dead if it exceeds the cap.
A run's pipeline, from file to file
Each stage is a collaborator injected into the orchestrator: it tests on its own.
The structuring idea

The two modes share everything but two things. Extraction, parsing, segmentation, budget guardrail, recomposition, QA, ledger, artifacts: identical. Only how cost is projected and how translation happens differ — which is exactly what the translationMode interface abstracts (4 methods: Init, Project, Translate, Cost). Adding a third mode means implementing this interface, not touching the pipeline.

2. The vocabulary, in one page

TermWhat it isWhere it lives
EPUB A ZIP archive containing XHTML, a spine (the reading order), and metadata. No DRM here: the project only handles open files. internal/epub
Segment The unit of translation: a <p> or <h1..h6> block. V1 is paragraph, not sentence. internal/segment
Placeholder A <x id="N"/> token that replaces inline markup during translation. The translator sees text, not HTML. segment/placeholder.go
TM (translation memory) A SQLite table hash → translation. A sentence already translated never goes back to a provider. internal/tm
NMT Neural machine translation — the draft. Three adapters: built-in dev server, self-hosted LibreTranslate, Google Cloud Translation v2. internal/translate
LLM The chat model that rewrites the draft in literary mode (Anthropic, OpenAI, DeepSeek). internal/llm, internal/literary
Series bible Style guide + character voices + address-form rules (tu/vous) + per-volume synopsis. Generated once, as input to a run, never as output. internal/narrative

COMET-QE A reference-free quality score: it rates a (source, translation) pair. Used to escalate weak drafts to the LLM, and to evaluate a run afterward. internal/eval
chrF A reference-based score: compares the produced translation to a human translation of the same edition. eval/chrf.go

3. Anatomy of an EPUB and parsing

An EPUB is a ZIP in which three entries matter to us: mimetype, META-INF/container.xml (which points to the OPF), and the OPF itself, which lists the manifest (all files) and the spine (the reading order). The parser follows this path rather than guessing file names.

A detail that matters

Segment.Node is a pointer into the parsed tree (segmenter.go:51). Restoring a translation means mutating the tree; recomposing means re-serializing the mutated tree into a new ZIP. There is never any string "re-gluing", so never any misalignment between what was translated and what is written.

Translated tags: p, h1…h6. Tags ignored entirely: head, script, style, code, pre (xhtml.go:12).

4. Segmentation & placeholders

This is the heart of "lose nothing". A novel paragraph rarely looks like pure text: it contains italics, links, notes. You can't send this HTML to a translator (it mangles it), nor strip it (you'd lose it). The solution: tokenize.

Two distinct treatments, depending on the child node encountered (placeholder.go:37):

  • Simple inline (a <em> that contains only text) → a pair of opening/closing tokens, and the inner text is exposed to translation. So the italic word gets translated, and it stays italic.
  • Everything else (nested, empty element, comment) → an opaque token: the subtree is set aside verbatim and put back as-is.
A paragraph's round trip — click to advance

Why restoration is atomic

A provider may return the tokens out of order, duplicated, or lose one. A simple presence check is not enough: open-1 open-3 close-2 close-4 is "balanced" and would rebuild two nested elements instead of adjacent ones — valid but wrong HTML, silently.

validateTokens therefore runs a full preflight — presence, uniqueness, opening/closing pairing — before touching the node. On failure, the node keeps its source markup: the segment degrades to "untranslated", QA counts it, and the run continues. Never any broken markup in the output.

5. Normalization, hash, and translation memory

Before being stored or looked up, a segment is normalized: multiple spaces collapsed, non-breaking spaces replaced, typographic apostrophes and quotes folded to their ASCII equivalent, em dashes → single dash, … → ... (normalizer.go:8). 

« He said,  “Wait.” »          →  He said, "Wait."      → sha256 → 3f9c…
« He said, "Wait." »           →  He said, "Wait."      → sha256 → 3f9c…   ← same TM entry

The TM key is sha256(normalized text). Two phrasings that are visually identical but typographically different therefore share their translation: this is what raises the reuse rate from one volume to the next.

An entry's engine carries meaning

A subtle trap, already fixed in the code

A TM entry carries an engine tag: nmt-google, nmt-libretranslate, literary, llm-postedit. In literary mode, a draft is never a hit (lookupTranslation rejects nmt-* engines). Without this rule, a draft written by an old run would be served back as a finished translation and that segment would never again be refined. Literary mode, moreover, only persists what the LLM produced — and only after placeholder restoration has succeeded.

The same SQLite database carries a second role: the spend ledger, append-only (table run_attempts). It answers "how much have I spent today / this month" and "how many free characters do I have left with this provider".

7. Literary mode and the series bible

The nmt mode produces a correct but flat draft. The literary mode adds an LLM pass that rewrites that draft with knowledge of the series: its style, each character's voice, who addresses whom formally, and what happened in the previous volumes. This knowledge is the series bible.

The prompt: one frozen part, one volatile part

Each LLM call is made of two messages (prompt.go:22):

BlockContentChanges when?
system
cacheable		 Absolute instructions · GUIDE_DE_STYLE · VOIX_DES_PERSONNAGES · REGLES_DE_VOUVOIEMENT_TUTOIEMENT · RESUME_DE_L_HISTOIRE · GLOSSAIRE · SOURCE_INTEGRALE_DU_CHAPITRE Once per chapter (the source changes), never between the batches of the same chapter.
user
volatile		 CONTEXTE_PRECEDENT (the last 1200 characters of French already produced) and the batch's segments in JSON. Every batch.

Putting the entire chapter source in the system block is counterintuitive but deliberate: it is constant across all the chapter's batches, so the prompt cache absorbs it after the first call. In the user turn, it would be resent at full rate on every batch. And it is what lets the model resolve a pronoun or a callback located elsewhere in the chapter.

Batches that repair themselves

A batch starts with 50 segments. If the response omits some (a small model that stops, truncated JSON), the code does not retry identically: it splits the missing segments into two halves and starts over, recursively, down to a single segment (translator.go:243). Whatever is left unanswered keeps its NMT draft.

The bible is an input, never an output

series-bible builds the bible before any translation, from all the volumes in the directory. Style, voices, and address forms come from all volumes; the summaries, however, are bounded: the bible that translates volume N only contains the synopses of volumes 1..N.

Why bound the summaries

A model that knows a character's true nature colors their dialogue from volume 1. The bounding is encoded in the identifier itself — ScopedSeriesID produces lumen@volume-01 — so neither the database schema nor the run flags had to change.

8. The cacheable prefix, or why freeze the bible

The --update-bible option lets the bible evolve chapter after chapter. Appealing on paper, ruinous in practice: the bible is in the prefix. Modifying it every chapter rewrites the cacheable prefix once per chapter instead of once per run — and leaves on disk a bible different from the one the run started with, so the re-run is no longer free or reproducible.

9. The cost model and the guardrails

The central property

There is only one cost model. estimate and the run guardrail both go through Model.Project. What estimate announces is therefore exactly what the per-book cap applies — they cannot diverge.

A projection that learns from what was measured

The per-character heuristic predicts the length of a translation. It does not predict what a model spends to produce it, and the gap is not a margin: on one measured chapter, 16,180 projected output tokens versus 53,409 consumed. A cap applied to the first figure lets through three times the work it thinks it authorizes.

The ledger therefore keeps, per attempt, the token counters and the (llm_provider, llm_model) pair that produced them; the next projection replaces its output heuristic with this measurement. The key is the model and its transport — verbosity carries over from one volume to the next, whereas nothing in a book's characters predicts it.

And it prices what's left, not the book

Before pricing, the projection asks the translation memory what it can already serve and drops those segments — a chapter entirely in memory doesn't even contribute a call's prefix, since no call will be made for it. This is what makes a resume viable: a run cut off at 80% used to project the whole book and could be refused by a cap sized for the 20% remaining.

QuestionAnswer
Does a cached nmt-* draft count as acquired? It depends on the mode, and it's translationMode.ReusesDrafts that decides: yes in NMT (the draft is the output), no in literary (it's an intermediate to redo). The projection applies exactly the lookupTranslation rule — otherwise it would let through a run that then pays for every segment.
So does estimated_cost_usd drop on a resume? No. This field stays the whole book with no reuse, because it is the base that cost_savings_usd subtracts from. The cap, in turn, is applied to the projection of the remaining work. Two numbers, two jobs.
What do we lose? The projection is no longer a property of the book alone: the same volume projects differently depending on the machine's memory. Accepted — it speaks about this run.

Transport is part of the price

Two facts about how the calls are issued change the bill by a factor, without changing the prompt at all. Neither is a setting: they are deduced from who executes the pass.

FactMeasured effectWhere it's decided
The CLI opens a fresh session on every call: nothing guarantees that a cacheable prefix survives to be re-read. Billed as rewritten on every call — an upper bound, not a description. Two runs of the same chapter: 46,970 then 13,927 write tokens per call, a factor of 3.4 on the very term being billed. Without the upper bound, the projection was ×1.9 to ×3.7 too low — always in the direction that lets a run through. llm.RewritesPrefixPerCall, read from the chat provider: no one should have to configure this.
The HTTP post-editor has no cache: one JSON POST per segment, without cache_control. Its prefix is paid at full rate on every call. That is what the code already asserted in a comment while its arithmetic billed one write then N re-reads. LLMPass.Uncached, carried by the pass: a property of the service that runs it, not of the account.

Two shapes of pass, because output isn't predicted the same way

LLMPass computes output as characters × expansion: the response reformulates the input, which is true of a translation. A summary doesn't work like that — it runs a few hundred tokens whether the chapter is two pages or forty. Using LLMPass for the bible build would amount to billing a 19,000-character chapter as if the summary returned 19,000 in response.

Hence SummaryPass, in the same package — a single place applies rates, that's the invariant — but with a bounded output rather than a proportional one, and with no term of prefix: each call carries a different chapter behind a system prompt of about a hundred tokens, well below any provider's cacheable minimum.

LLMPass (translation)SummaryPass (bible)
Outputproportional to inputbounded: ~274 tokens per chapter summary, ~400 per synopsis
Prefixbible + chapter source, repeated and cacheablenone — nothing to cache
Without ratesprojects 0still projects the tokens: it's the command you run on a subscription, where the token is the only figure that counts

What makes the projection correct is counting the calls and not only the segments: each call repeats the prefix. This is why LLMPass separates Segments, Chars, Calls, PrefixChars, and details the shape per chapter rather than on average: a long chapter has both a bigger prefix and more calls to re-read it, and the average crushes precisely that covariance.

Two billing subtleties are worth knowing:

  • The free tier is counted in characters per calendar month, not in dollars. A fully free run therefore still consumes the allocation against which the next one will be billed — hence the dedicated metric translation_nmt_chars_total.
  • The characters counted are those the adapter actually sent (translate.Meter), not those reconstructed from the segments: retried attempts and glossary-protected text are invisible to the second count.

12. Extending the project: four recipes

Recipe 1 — Add an NMT provider

Implement translate.Translator:

type Translator interface {
    Translate(ctx, Request) (Response, error)
    TranslateBatch(ctx, BatchRequest) ([]Response, error)
    Engine() string          // TM tag, e.g. "nmt-deepl" — MUST start with "nmt-"
}
  1. Create internal/translate/deepl.go and embed charMeter so that the characters sent are counted (free tier + ledger).
  2. Register the name in NewProvider and, if an endpoint is needed, in RequiresEndpoint.
  3. If the provider has a free tier or a public rate, add it to config.applyProviderDefaults — otherwise a paid provider would be selectable with a guardrail that projects $0.
  4. If it requires credentials, add it to translate.RequiresAPIKey. Validation happens at provider construction, never at config load — otherwise estimate, which makes no call, would refuse to start without a key, and would demand a secret from the password manager just to do a sum.
  5. The nmt- prefix is not cosmetic: it's what prevents a draft from being served back as a finished translation in literary mode.
Recipe 2 — Add an LLM provider

Implement llm.ChatClient:

type ChatClient interface {
    Chat(ctx, ChatRequest) (ChatResponse, error)
}
  • If the API is OpenAI-compatible, there is nothing to write: just LLM_CHAT_PROVIDER=openai + LLM_BASE_URL + LLM_MODEL.
  • The transport does not have to be HTTP. llm.CLIChatClient (LLM_CHAT_PROVIDER=claude-cli) launches a subprocess per completion and fills the same ChatResponse; the SQLite cache keeps working without knowing, since it keys on the model and the messages, not on the transport.
  • Otherwise, fill ChatResponse completely — including InputTokens, OutputTokens, CacheReadInputTokens, CacheCreationInputTokens, and StopReason. These fields are not decorative: the run's actual cost is derived from them, and StopReason distinguishes a refusal from a truncation.
  • The SQLite cache applies automatically by composition (CachedChatClient{Inner: …}): nothing to do on the adapter side.
Recipe 3 — Add a translation mode

Implement translationMode in internal/pipeline/mode.go and route it in newTranslationMode. The four methods:

  • Init(result) — stamp the mode and its own fields.
  • Project(chapters, usedFreeChars) — the worst case without TM reuse. This is what the cap compares against; underestimating here amounts to disabling the guardrail.
  • Translate(...) — fill the targets, restore the placeholders, increment the counters as you go so that a mid-way failure leaves an exact trace.
  • Cost(result, usedFreeChars) — pure, callable after a failure.

Also remember: the value of the --mode flag in cli/flags.go.

Recipe 4 — Add a QA check or a metric
  • QA check: add a check* in qa.Evaluate, a field in Report, and decide whether it enters Report.Passed() (blocking) or only Warnings.
  • Metric: write it in writeMetrics and in docs/ARCHITECTURE.md §10. The document is the contract: "a metric added to the code belongs there too".
  • If it doesn't always make sense, emit it conditionally rather than publishing a zero that would read as a measurement.

13. The invariants not to break

These rules are decisions paid for by bugs already encountered. They are covered by tests; if a test opposes your change, it probably documents one of these points.

#InvariantWhat breaks if you ignore it
1Placeholder restoration is atomic: validate before mutating.Silently wrong markup, or lost content.
2An nmt-* draft is never a TM hit in literary mode.The segment skips refinement — permanently.
3You persist after Restore, never before.A translation that rebuilds bad markup gets stored as "finished".
4Spend is recorded in a defer, including on failure.The provider does not refund; the next projection becomes wrong.
5A ledger read that fails stops the run (fail closed).The cap is silently bypassed.
6Tokens are counted before the batch's error check.A refusal or truncation is billed but counted as zero.
7The stable prefix stays byte-for-byte identical across an entire run.The prompt cache no longer triggers: ×10 on the input cost.
8Errors are wrapped unable to <context>, err: %w, with sentinels in errors.go.errors.Is no longer works, so neither does the mapping to exit codes.
9A failed LLM batch degrades the chapter, it does not cancel it — but it is logged.Either you lose the successful batches, or you no longer know why part of it isn't refined.
10Artifacts are written even when QA fails.A failed run becomes undiagnosable.
11The displayed progress is never a data source: it is derived from the same counters as report.json, and a segment is reported once — fresh in the NMT loop or via literary.Translator.OnBatch, reused on a TM hit. The displayed amount comes from mode.Cost, the one that writes actual_cost_usd: the last figure seen is the report's.A bar that exceeds 100%, or that freezes for a whole chapter, and a CLI whose stdout is no longer parseable.
12estimate and the run guardrail apply the same calibration, read from the same ledger. And a calibration that cannot be read leaves the heuristic in place instead of stopping the run — unlike the free-tier read, which fails closed.A projection that changes its base between two invocations, or a run refused because an estimate refinement couldn't be read.
13LLM tokens are accumulated in a single place: the OnBatch hook. Outcome.Usage carries the same tokens seen per chapter — adding both bills twice.An exactly doubled cost, invisible without a reference measurement.
14A rate limit (llm.ErrRateLimited, an HTTP 429) stops the chapter, it does not degrade it — it's the only batch error that does not degrade.The rest of the book fails batch by batch silently and comes out as an NMT draft — which literary mode does not persist, so with nothing to resume.
15The projection applied to the cap prices the remaining work; estimated_cost_usd stays the whole book with no reuse. These are two different numbers and they have two jobs.Either a resume refused for a bill it won't pay, or cost_savings_usd dropping to zero exactly on the runs where memory worked the most.
