1. Prerequisites and installation

The toolchain is declared in mise.toml: one command installs it, at the same versions for everyone. Two prerequisites stay manual. 

# macOS (Homebrew) — the only two tools to install yourself
brew install mise 1password-cli

# Fetch and prepare the project
git clone git@github.com:ECecillo/tomeshift.git tomeshift
cd tomeshift
mise trust                        # mise won't run a repo's config without consent
mise install                      # go, java, just, golangci-lint, rg, python, uv
cp .env.example .env.local        # NON-SECRET config, gitignored
just preflight                    # config + tools + 1Password session + NMT health
go build -o ./bin/tomeshift ./cmd/tomeshift

Why mise rather than a list in a README

The Justfile calls ten tools; the old preflight checked five. python3, sqlite3, uv and docker were declared nowhere: they failed with command not found at the exact moment you ran just bible or just compare. mise.toml makes the list executable, and in particular pins the Java ≥ 21 that epubcheck requires and that only existed in a sentence.

Startup pitfall

Broken GOROOT (go: cannot find GOROOT directory) → prefix the commands: env -u GOROOT go test ./.... Never put this prefix in a Justfile recipe.

Secrets are not in a file

Two files, two roles — that's the rule to remember:

FileContentVersioned?
.env.localNon-secret configuration: provider, database paths, caps, prices.no (gitignored)
.env.opReferences op:// to the 1Password vault. No values.yes
# .env.op — committable as-is, these are just pointers
TOMESHIFT_LLM_API_KEY=op://Dev/anthropic-epub-translator/credential
TOMESHIFT_NMT_API_KEY=op://Dev/gcp-cloud-translation/credential

The recipes that call a provider are wrapped in op run --env-file=.env.op --: the key is resolved at launch, lives in the process's memory for the duration of the command, and nowhere else. The others are not — so estimate, glossary-suggest and eval-ref never ask for a credential, since they make no calls.

What biometrics guarantees, exactly

The Touch ID prompt appears when the 1Password app is locked. As long as it's unlocked, op authorizes without asking again. The guarantee you buy is therefore "the secret is never at rest on disk and doesn't leak into the environment", not "a human approved this specific run". For the latter, set the app's auto-lock aggressively.

3.1 Google Cloud Translation — the API key

  1. GCP console → create or pick a project.
  2. Enable billing on the project. This is required even for the free tier: without it, the API refuses calls even though nothing would be billed.
  3. "APIs & Services" → "Enable APIs" → enable Cloud Translation API.
  4. "APIs & Services" → "Credentials" → "Create credentials" → API key.
  5. Restrict the key to the Cloud Translation API only ("Restrict key" → API restrictions). An unrestricted key grants access to everything enabled on the project.
The free tier, precisely

500,000 characters per calendar month, shared between Basic and Advanced and across the whole project — about one volume. Only the overage is billed. The pipeline's counter is its own run ledger: if characters were consumed outside this tool this month, the projection underestimates by that much. You then have to lower NMT_FREE_CHARS_PER_MONTH by hand.

3.3 Store the keys in 1Password

The project expects items of category API Credential, whose secret field is named credential — that's what the op://<vault>/<item>/credential references in .env.op point to. 

# 1. Enable the CLI ↔ app integration (it's what triggers Touch ID):
#    1Password app → Settings → Developer → "Integrate with 1Password CLI"

# 2. Find YOUR vaults and YOUR accounts — there is no default name:
op account list        # the connected accounts
op vault list          # the current account's vaults

# 3. If several accounts are connected, pin the one to use in .env.local
#    — this applies to `just` recipes, NOT to your terminal:
#      OP_ACCOUNT=my.1password.eu

# 4. Create the items. --account is explicit here: the commands below
#    run in YOUR shell, which does not source .env.local.
op item create --account my.1password.eu --category="API Credential" \
  --vault=Personal --title="anthropic-tomeshift" \
  credential="sk-ant-…"

op item create --account my.1password.eu --category="API Credential" \
  --vault=Personal --title="gcp-cloud-translation" \
  credential="AIza…"

# 5. Check that each reference resolves (that's what `op run` will do):
op read --account my.1password.eu "op://Personal/anthropic-epub-translator/credential"
op read --account my.1password.eu "op://Personal/gcp-cloud-translation/credential"
Two pitfalls, in this order

1. The vault. Personal above is a name, not a default: op item create --vault=X fails with "X" isn't a vault in this account if X doesn't exist for you. op vault list first, then adapt .env.op — don't rename your vaults to match a doc.

2. The account. An op:// reference names a vault, never an account. With a work account and a personal account connected at the same time, op resolves against the one it considers current — hence a personal key looked up in the employer's vault. The symptom is misleading: "Personal" isn't a vault in this account looks like a vault problem when it's the account that's wrong.

And the two settings don't cover the same thing. OP_ACCOUNT in .env.local decides for the just recipes, which source that file; your terminal does not source it, so the op item create and op read you type by hand need --account (or an export OP_ACCOUNT=… in the session). just preflight warns you if several accounts are connected without pinning.

In the app, right-click the field → "Copy Secret Reference" gives the exact op://… string, vault included.

Personal project, personal account

If your machine has both accounts, put this project's keys in the personal account. A key stored in a vault managed by the employer falls under their administration and disappears when you leave; that's not the place for a personal project.

6. Reference of the seven commands

run — translate a book

tomeshift run --input <f.epub> --output-dir <dir> --source-lang en --target-lang fr \
  [--mode nmt|literary] [--series <id>] [--glossary <f.json>] [--run-id <id>] \
  [--update-bible] [--resume] [--no-progress]
FlagDefaultEffect
--inputrequiredThe source EPUB. Its filename (without extension) becomes the book_id.
--output-dirrequiredArtifacts go into <output-dir>/<run-id>/, not directly inside it.
--source-lang / --target-langrequiredV1 only accepts en → fr. Any other value is rejected at flag parsing (exit 2), before any work.
--modenmtnmt: draft + optional escalation. literary: LLM rewrite of each fresh segment, with mandatory bible.
--series—Required if --mode literary. Target the volume's bounded bible: lumen@volume-01. Missing or invalid bible = immediate failure.
--glossary—locked terms are masked before the call and re-substituted after. A residual violation fails the QA gate.
--run-idUTC timestampNames the artifacts folder. Reusing the same identifier overwrites the previous artifacts.
--update-biblefalseLets the bible evolve during the run. discouraged Breaks the cacheable prefix (≈ ×10 on cost) and makes re-runs non-reproducible.
--no-progressfalseTurns off the progress bar. It only shows anyway if someone can see it (see the box below): in CI or to a file, there's nothing to turn off. The flag is for cases the detection doesn't cover — a captured session, a screen reader, or a log built through a relay.
--resumefalseToday a simple logged marker: resumption in fact comes from the translation memory, which re-serves everything already translated. Restarting an interrupted run doesn't re-pay for work already done.

During the run, a line rewritten in place on stderr tells you where things stand:

  • ch only appears in literary mode: NMT mode flattens the book and doesn't track chapters.
  • tm is the share of segments served by the translation memory. It's what explains a bar that advances fast then slows: hits are instant, provider calls are not.
  • The amount is the real cumulative spend, computed by the same cost model as actual_cost_usd in report.json: the last number shown is the one the report carries. It doesn't appear when it's 0 — a self-hosted engine with no LLM pass costs nothing, and a column of $0.0000 would be noise. In literary mode it only advances at chapter seams: that's where the provider returns the tokens it has consumed.
  • The ETA is withheld before 10% of the book — extrapolating the speed of a burst of TM hits would announce a few seconds for an hour of work.
  • The last line, though, goes to stdout: it's the only parseable output, and the bar never mixes into it.
When it shows, and why it's not "stderr is a terminal"

That was the first rule, and it turned off the bar exactly on the commands you watch. Any recipe that needs a key is wrapped in op run, and 1Password masks secrets in the streams it relays — which it can only do by replacing them with pipes. Measured through it, stderr comes back as prw-rw----. The frames, though, pass through intact: op forwards carriage returns byte for byte.

stderr is…BarWhy
a terminal (character device)✅The simple case.
a pipe, and the process has a controlling terminal✅Something relays our output rather than storing it, and someone is there. op run, | tee.
a pipe, without a controlling terminal❌CI, cron, background task: nobody is watching.
an ordinary file❌2> run.log — that's the redirection the distinction protects: a readable log matters more than a bar nobody asked to store.

What we can know is that the output is relayed and a human is present; what we can't know is what the relay does with it next. A > log 2>&1 through such a relay would collect the carriage returns — that's what --no-progress is for.

estimate — project the cost without paying

tomeshift estimate --input <f.epub> [--escalation-rate 0.15]

Parses and segments the book, translates nothing, calls no API, and prints three scenarios: NMT only, hybrid (the --escalation-rate fraction of segments goes to the LLM), full LLM.

Why this command is reliable

estimate and the run's guardrail go through the same cost model, read the same free-tier counter in the ledger and apply the same calibration. What estimate announces is what the per-book cap applies. Corollary: if the LLM prices are not set in .env.local, the projection is $0 and the cap compares nothing anymore.

Calibration: what past runs measured

The per-character heuristic predicts the length of a translation; it doesn't predict what a model spends to produce it. On chapter 97 of vol33 it projected 16,180 output tokens against 53,409 consumed — 207 per segment instead of 63. Not a margin, a factor.

The ledger (run_attempts) therefore keeps the token counters of each attempt, with the (llm_provider, llm_model) pair that produced them. The next run — and estimate — replace the output heuristic with that measurement. The key is the model and its transport, not the book: a model's verbosity carries from one volume to the next, whereas nothing in a book's characters predicts it.

  • An attempt that died before its LLM pass, or whose transport reports no usage, calibrates nothing: the average only counts attempts that have both segments and tokens. Otherwise the projection would get cheaper with every crashed run.
  • The average is weighted by segments: a 4,000-segment volume says more about a model than a 20-segment test, and averaging the two ratios would give them equal weight.
  • No ledger = nothing measured. estimate doesn't create one: it's a dry command, it doesn't leave a database behind it.
Two corrections that push the numbers up — deliberately
  • The CLI transport is billed as if it rewrote its prefix on every call. With LLM_CHAT_PROVIDER=claude-cli, each invocation is a fresh session: nothing guarantees that a prefix survives to be re-read. It's an upper bound, not a description — see the two measurements below. Without it, the projection was ×1.9 to ×3.7 too low on those same runs, always in the direction that lets a budget cap pass a run. A cap that overestimates refuses work it could afford; a cap that underestimates bounds nothing.
  • The escalation pass gets no cache. The HTTP post-editor is a JSON POST to an arbitrary endpoint, with no cache_control: its prefix is paid at full price on every call — which the code comment already asserted ("paid once per segment") while the arithmetic billed one write then N cheap re-reads. The hybrid line therefore rises sharply. It's an upper bound, and the conclusion it carries is the one the project repeats: escalation is expensive per word.

The projection prices what's left to do

It consults the translation memory before pricing, and drops what it can already serve. That's what makes a resume possible: a run cut off at 80% — by an exhausted quota, by Ctrl-C — still projected the whole book and could be refused by a cap sized for what remained. The cost of this read is nil at the scale of a projection: point lookups on an indexed column, no provider call, so estimate does it too.

Two consequences to know:

  • A draft is only reusable for the mode it's the output of. In NMT mode a cached draft is the final result, so free; in literary it's an intermediate to redo, and counting it as acquired would pass a run that then pays for each segment. The projection therefore applies the same rule as the translation.
  • estimated_cost_usd in report.json stays the whole book without reuse, and is not the figure the cap is applied to. That's intentional: it's the only base cost_savings_usd can subtract from to mean "what the memory saved". The two coincide on a fresh book and diverge on a resume.
  • The price: the projection stops being a property of the book alone. The same volume projects differently depending on the machine's memory. That's by design — it speaks about this run.

What two runs of the same chapter measured

Same chapter (97 of vol33, 258 segments, 6 batches), same model (claude-sonnet-5 via claude-cli), same bible v3, two weeks apart:

Runcache writeper callcache readtotal inputoutput / segmentnotional cost
ch97-sonnet · Aug 8281,81946,970191,000472,833207$1.9153
ch97-cli · Aug 2383,56013,927201,885285,457160$0.9950

The first looks exactly like six full rewrites of the prefix. In the second, the reads dominate: the provider's content cache clearly triggers on its own, which the setup posed as its open question. Same transport, a factor of 3.4 apart on the very term the upper bound bills.

Hence the takeaway: on this transport, the projection bounds a spend, it doesn't predict it. On the Aug 23 run it announced $1.1373 for $0.9950 actual (+14%); on the Aug 8 one the same model would have announced $1.1373 for $1.9153 (−41%). The error changes sign — that's the sign you hold a bound, not a law. The old model, for its part, was always wrong in the same direction.

series-bible — build the bible before translating

tomeshift series-bible --input-dir ./books/lumen --series lumen [--samples 3] [--merge] [--dry-run] [--from-volume N]
FlagDefaultEffect
--input-dirrequiredAll the .epub in the folder, in publication order inferred from the filename.
--samples3Documents sampled per volume for style, voices and forms of address. Note: they all go in a single call, so the input grows with the series — see the box below.
--mergefalseEnriches existing bibles instead of overwriting them.
--dry-runfalsePrints the cost projection and stops before the first call. Nothing is created — not even the bible's database.

The cost projection

estimate prices the translation of a book; it can't price a bible build, which is another kind of work. series-bible therefore carries its own projection, printed systematically before the first call, and the per-book cap applies to it. 

tomeshift series-bible --input-dir ./epub/lumen --series lumen --samples 3 --dry-run

The --samples pitfall

--samples looks like a per-volume setting, but the style pass concatenates all the samples into a single call. On 33 volumes, --samples 8 sends 966,526 tokens in one request — beyond Haiku 4.5's context window (200K), and absurd everywhere else. The command warns you above 200,000 tokens. --samples 3 fits in 9,703 tokens.

Without LLM prices set

The projection still prints the tokens — that's the case with the claude-cli setup, where there's no marginal dollar and the token is the only figure that counts. It says so explicitly rather than silently showing $0.0000, and no cap applies then.

Output: one bible per volume (lumen@volume-01, lumen@volume-02, …) plus lumen = the bible of the most recent volume. A bible's synopses are bounded to volumes 1..N so as not to reveal the end of a story you're starting. Cost: about 1 + (chapters + 1) LLM calls per volume, once, never replayed.

Consequence to know

Regenerating the bible changes the prompts' prefix, so invalidates the LLM cache once. That's intentional: a one-off cost per regeneration, instead of a per-chapter cost. Already-translated volumes are not re-translated automatically.

style-profile — seed the bible from a single volume

tomeshift style-profile --input <f.epub> --series <id> [--samples 3] [--merge]

A single LLM call, a single volume, no synopsis. Useful for a standalone book or to fix the style of an existing bible with --merge. series-bible supersedes it for series work.

glossary-suggest — extract proper nouns

tomeshift glossary-suggest --input <f.epub> [--out glossary.json] [--min-count 3]

Free, heuristic, no configuration required — it's the only command that doesn't load the config. It produces a JSON skeleton to curate by hand: keep the real names, write the French form, remove the noise, check locked. Raising --min-count reduces noise and lets rare names slip through.

  { "term_en": "Elena", "term_fr": "Elena", "locked": true },

eval — measure quality

# chrF: requires a human reference from the SAME edition
tomeshift eval --candidate ./runs/<id>/translated.epub --reference ./ref-fr.epub

# COMET-QE: reference-free, requires an active COMET service
TOMESHIFT_COMET_ENDPOINT=http://localhost:8000/score \
  tomeshift eval --segments ./runs/<id>/segments.jsonl
Choosing the right metric

Comparing a light novel translation to a web novel reference gives a catastrophic chrF that says nothing about quality: they aren't the same texts. Without an aligned reference, COMET-QE is the honest metric. The per-book average lands in report.json (avg_quality_score) and metrics.json.

batch — process a folder of books

tomeshift batch --input-dir ./books/serie --output-dir ./runs \
  [--glossary ./glossary.json] [--reference-dir ./refs] [--no-progress]
  • NMT mode only — no literary mode in batch.
  • A TM and a glossary shared across the books: volume 2 reuses volume 1's sentences, and terminology stays consistent throughout.
  • A failed book doesn't stop the following ones; the first failure sets the exit code.
  • Artifacts go into <output-dir>/<book-id>/, plus an aggregated batch-report.json.
  • --reference-dir: if <dir>/<book-id>.epub exists, a chrF is computed for that book and injected into the aggregated report. Without a reference for a given book, it's silently skipped.
  • Each book has its own progress bar, prefixed with its book_id and closed by the book's recap line. --no-progress turns them all off.
  • Ctrl-C stops cleanly between two books.

8.1 The experimental setup: Claude Code CLI instead of the API

LLM_CHAT_PROVIDER=claude-cli replaces the HTTP call with a claude -p --output-format json subprocess, authenticated by the application's session. No API key, so no op run wrapper: the Justfile detects it and launches directly. LLM_MODEL then accepts a CLI alias (opus, sonnet, haiku) or a full model name. 

TOMESHIFT_LLM_CHAT_PROVIDER=claude-cli
TOMESHIFT_LLM_MODEL=opus
TOMESHIFT_LLM_CLI_BIN=                  # empty = "claude" from the PATH
# The prices stay set: they bill nothing here, they turn the
# per-book cap into a consumed-quota indicator.
TOMESHIFT_LLM_INPUT_PER_MTOK_USD=15.00
TOMESHIFT_LLM_OUTPUT_PER_MTOK_USD=75.00
The measurement that makes the setup viable

The adapter passes --system-prompt, which replaces the agent's system prompt, and --tools "", which disables the tooling. Without these two options, every invocation drags in Claude Code's full preamble. Measured on 8 August 2026, on a one-line prompt:

InvocationCached input tokensAPI equivalent
bare claude -p48,870$0.2936
with --system-prompt + --tools ""2,027$0.0126

24× less overhead per call, and a volume makes more than sixty-eight of them.

What this setup makes you lose
  • The budget guardrail stops describing a real spend. A subscription has no marginal cost. Keeping the model's published prices turns the per-book cap into a quota indicator — it's the best substitute the pipeline can compute, but it's no longer a bill.
  • cache_control escapes you. The Anthropic adapter marks the stable prefix explicitly; here the CLI decides. The prefix stays identical byte for byte between a chapter's batches, so the provider's content cache can trigger on its own. llm_cache_read_tokens in report.json is the number that tells you — the first to look at after a real run.
  • No native structured output. The CLI has no equivalent to the API's JSON schema: the schema becomes an instruction. The tolerant decoder and the half-batch recovery absorb the difference, at the cost of a few more degraded batches.
  • MaxTokens is ignored (the CLI doesn't expose the setting): the model's limit applies.

Before launching a volume, the end-to-end check — it consumes quota, so it's explicitly optional: 

TOMESHIFT_LIVE_CLI_TEST=1 TOMESHIFT_LLM_MODEL=opus \
  go test ./tests/integration/ -run TestLiterary_ClaudeCLI -v
# → translates 3 segments, checks the placeholders, and prints the counters:
#   usage: input=2 output=164 cache_read=0 cache_creation=2847

9. Reading a run's artifacts

runs/20260808-142312/
├── translated.epub   ← the book
├── report.json       ← segments, TM hits, tokens, costs, QA block
├── segments.jsonl    ← 1 line per segment (input to eval --segments)
├── metrics.json      ← flat metrics, canonical names
└── logs.ndjson       ← structured logs
Artifacts are written even if QA fails

A run that exits with exit 5 still produced its EPUB and its reports: that's what makes diagnosis possible. First look, in report.json, at the qa block: placeholder_restore_ratio (threshold 0.995), untranslated_segments, missing_spine_docs, glossary_violations, epubcheck_passed.

The report.json fields used for calibration

FieldWhat it says
llm_pass_segmentsHow many segments the LLM pass carried, usable result or not — to be distinguished from llm_segments, which counts those it improved. It's the denominator that goes with the token counters: dividing a degraded batch's tokens by the segments it didn't deliver would make a model all the more "verbose" the worse it behaves.
llm_provider / llm_modelWho consumed these tokens. It's the key under which the measurement is reusable. Set in literary mode only: the HTTP post-editor is chosen by endpoint, not by model, and reports no usage to attribute.
llm_cache_creation_tokensThe prefix written to the cache. On claude-cli, dividing it by the number of calls shows whether it's rewritten every time — it's the first number to look at to understand a bill.

A segment's statuses in segments.jsonl

StatusMeans
reusedServed by the translation memory. Zero calls, zero cost.
translatedNMT draft. In literary mode, it's the sign that the LLM couldn't refine it (degraded batch) — look for the corresponding warning in logs.ndjson.
post_editedRewritten by the LLM, placeholders checked. It's the nominal status in literary mode.

What compose doesn't cover, by design

Literary mode works via app (it reads .env.local, hence the API key), but the LLM is an external API, not a hosted service: to enable it in a container you must adapt the app service's command: (--mode literary --series … --glossary …).
